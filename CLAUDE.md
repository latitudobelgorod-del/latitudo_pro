# Проект: сайт Latitudo на 1С‑Битрикс

## Что это
Корпоративный сайт компании **Latitudo** (террасная доска, заборы, фасады из ДПК).
Делается на CMS **«1С‑Битрикс: Управление сайтом»** (PHP). Дизайн готов — **исходные макеты живут
в Figma** и достаются через API по токену.

## Суть сайта (из ТЗ)
- Домен `latitudo.pro`. **5 филиалов = 5 поддоменов:** `msk` (Москва), `belgorod`, `vrn` (Воронеж),
  `krd` (Краснодар), `rnd` (Ростов). Сайт один, контент части блоков меняется по поддомену (городу).
- **1 главная страница + страницы‑разделы** (Террасная доска, Строительство террас, Заборы, Перила и
  ограждения, Ступени, Все изделия из ДПК, Перголы). URL раздела: `msk.latitudo.pro/stupeni`.
  **Папок разделов в структуре сайта НЕТ** — все лендинги рисует один диспетчер
  `local/routes/catalog-landing.php`, на который правило в `urlrewrite.php` (последнее в массиве)
  отправляет односегментные адреса. Новый раздел заводится в админке и открывается сам, без кода.
  Индивидуальные блоки раздела: включаемые области `/include/<slug>-story.php` и
  `/include/<slug>-benefits.php` (файла нет → блока нет) + галочки `UF_SHOW_ABOUT`,
  `UF_SHOW_HOW_WE_WORK`, `UF_SHOW_VIDEO`, `UF_SHOW_REVIEWS` у раздела.
  Новая база → прогнать `php tools/setup-landing-blocks.php`.
- **`robots.txt` и `sitemap.xml` — тоже роуты, файлов на диске НЕТ**
  (`local/routes/robots.php`, `local/routes/sitemap.php`, правила в `urlrewrite.php`).
  Причина: обоим нужен абсолютный адрес ТЕКУЩЕГО хоста, а docroot у голого домена и
  пяти поддоменов филиалов общий — карту на чужом хосте Яндекс не принимает.
  Состав карты берётся из `latitudoCatalogLandings()`, то есть новый раздел из админки
  попадает в неё сам; служебные разделы отсекает снятая галочка `UF_SHOW_MENU`.
  ⚠️ Положишь в корень настоящий `robots.txt` — Apache начнёт отдавать файл,
  и роут молча перестанет работать (mod_rewrite не доходит до Битрикса, если файл есть).
- **Канонические хосты.** Филиалов пять, но живых хостов было девять: `www.`, `msk.`,
  `rnd.`, `krd.` открывали то же самое, что `latitudo.pro`, `rostov.` и `krasnodar.`.
  Теперь дубли отдают **301** на канонический адрес — `latitudoCanonicalHostRedirect()`
  в `include/region.php`, вызов из `init.php`. Канонический вид берётся из карт
  `LATITUDO_REGION_SUBDOMAIN` / `LATITUDO_REGION_ALIASES`, новый алиас достаточно
  дописать туда. Поддомены филиалов друг на друга НЕ схлопываются (контент разный),
  `/bitrix/` и не-GET запросы исключены.
  ⚠️ Код ответа ставить только через `CHTTP::SetStatus()`: под FastCGI статус идёт
  заголовком `Status:`, роутер Битрикса выставляет там «200 OK» до подключения
  страницы, и `header(..., 301)` его не перебивает — получится 200 с `Location`.
- **Адреса страниц — без `.php`:** `/policy`, `/terms`, `/search/map`. Правила в
  `.htaccess` (301 с `.php` на чистый адрес + внутренняя подмена обратно). Со слешем
  на конце (`/policy/`) намеренно 404 — иначе дубль для поиска.
- **Аналитика и согласие на cookie — ДВА УРОВНЯ СБОРА.** Счётчик Метрики №110963911
  работает только на проде, а глубина сбора зависит от куки `latitudo_cookie_consent`
  (проверка серверная, в `header.php`): `1` — полный сбор с вебвизором и картой кликов;
  пусто (не выбирал) — базовый, только визиты и цели; `0` — счётчика нет вовсе.
  Граница проведена по тяжести сбора: вебвизор пишет ввод в поля форм, визит и цель —
  несопоставимо меньше. Cookieless-режима у Метрики нет, поэтому «считать, не ставя
  cookie» невозможно, и базовый уровень — осознанный компромисс заказчика.
  ⚠️ Вебвизор после «Принять» включается со следующей страницы: повторный
  `ym(id,'init')` с другими параметрами Метрика игнорирует.
- **Цель `marquiz-finish`** — единственная на все заявки (форма + оба обработчика Envybox
  + завершение квиза), и это **намеренное решение заказчика** (подтверждено 2026-08-17):
  разводить по каналам не предлагать. Следствие принимается осознанно — в отчётах Метрики
  форму, звонок и квиз не отличить.
  ⚠️ Происхождение цели: это **автоматическая цель Метрики от Marquiz** (их всего четыре:
  `marquiz-start`, `marquiz-result`, `marquiz-finish`, `marquiz-payment-success`), она
  создаётся, когда счётчик вписан в квиз в кабинете Marquiz и в счётчике включены
  «Автоматические цели». Мы в неё дописываем свои события. Значит если интеграцию Marquiz
  отключат или «Автоматические цели» снимут, цель может исчезнуть — и конверсии формы и
  обратного звонка перестанут считаться МОЛЧА. Пропали цифры без правок кода — проверять
  это первым делом.
  Отправляется под двумя проверками: `window.ym && latitudoMetrikaAllowed()` — вторая нужна
  на случай, если «Отклонить» нажали уже после загрузки базового счётчика.
  Заявки, у которых цель НЕ дошла (mc.yandex.ru срезал блокировщик — заглушка `ym` есть,
  а `tag.js` нет), досылаются сервером через API офлайн-конверсий по `yclid`:
  `include/metrika-conversions.php` → очередь → крон `tools/metrika-upload-conversions.php`.
  Только трафик Директа, только форма заявки. Явный отказ **не обходим**.
  Настройка прода (токен `metrika.token`, цель, крон) — в `WORKFLOW.md`.
- Пункты меню = **якоря** на блоки. Детальных страниц (товаров, портфолио, отзывов, акций) **нет**.
- **Инфоблоки** (контент, редактируемый в админке): «Каталог продукции» (6 разделов), «Реализованные
  проекты», «Отзывы», «Магазины / Регионы» (5 городов — телефоны/адреса/реквизиты по поддоменам).
- **Включаемые области** (сквозные блоки для всех страниц): Преимущества, О компании, Дилерам и партнёрам,
  «Посетите магазин в …», Контакты, шапка, подвал.

### RATE-LIMIT — лимит высокий, но кэш всё равно первичен
Файл лежит в нашей Professional-команде, где у нас **Full/Editor seat** → Tier-1 (`GET file`,
`GET file nodes`, `GET image`) = **15 запросов/мин** (а не 6/мес, как было на View-seat).
Поузельные запросы и рендер иконок теперь допустимы. Но файл тяжёлый (162 МБ), поэтому режим
работы прежний — **один `pull.sh` → дальше оффлайн по кэшу**:
```bash
bash tools/figma/pull.sh                                   # 1 запрос → .figma-cache/file.json
PYTHONUTF8=1 python tools/figma/inspect.py css 537:19091   # дальше — оффлайн, без API
```
Подробности — `tools/figma/README.md`. Диагностика при 429: заголовки `X-Figma-Rate-Limit-Type`
(`high` = Full/Dev seat, `low` = View), `X-Figma-Plan-Tier`, `Retry-After`.

### Рецепт обращения к API (Windows / Git Bash + Python)
Команды — на bash-синтаксисе, запускать **в Git Bash, не в cmd.exe** (иначе `tr` не найдётся,
`$TOKEN` не подставится и Figma вернёт `Invalid token` на пустой токен).
Токен лежит в файле `figma.token` в корне проекта (закрыт от HTTP через `.htaccess`,
**не деплоить на прод**). Читать: `TOKEN=$(tr -d ' \r\n' < figma.token)`.
```bash
TOKEN=$(tr -d ' \r\n' < figma.token); KEY='hswIkVyGSXLn1wXaJ7w0Ps'
# 0) Проверка токена (лимит Tier-1 НЕ тратит) — вернёт email владельца:
curl -s -H "X-Figma-Token: $TOKEN" "https://api.figma.com/v1/me"
# 1) Структура файла (страницы и фреймы):
curl -s -H "X-Figma-Token: $TOKEN" "https://api.figma.com/v1/files/$KEY?depth=2"
# 2) Конкретные узлы (геометрия, цвета, текст):
curl -s -H "X-Figma-Token: $TOKEN" "https://api.figma.com/v1/files/$KEY/nodes?ids=537:19091&depth=2"
# 3) Рендер узла в картинку → вернёт S3-URL, его и качать:
curl -s -H "X-Figma-Token: $TOKEN" "https://api.figma.com/v1/images/$KEY?ids=537:21935&format=png&scale=2"
#    Для иконок/логотипа: format=svg
```
Если `Invalid token` пришёл из Git Bash — токен реально протух, пересоздать в Figma
(Settings → Security → Personal access tokens, scope `File content: read`) и заменить файл.
Грабли окружения:
- Парсить JSON и печатать кириллицу — Python с `PYTHONUTF8=1` (иначе `UnicodeEncodeError` в cp1252).
- Windows-Python **не видит** `/tmp` как Git Bash: класть временные файлы внутрь проекта.
- Убирать `\r` из URL-списков перед скачиванием (`tr -d '\r'`), иначе ломается путь.

## Технический стек и локальная среда
- **CMS:** 1С‑Битрикс: Управление сайтом, редакция **«Старт»** (лицензия активна на проде).
  Инфоблоки в «Старт» **входят** (прежняя заметка «в Старте их нет» была неверной). Из редакции
  убраны неlicензионные модули (`catalog`, `sale`, `form`, `bizproc` и др. — 29 шт.) для закрытия
  LICENSE_VIOLATION; форма заявки поэтому на `bitrix:main.feedback`, а не «Веб-формах». Компоненты
  `catalog.section*` берём из модуля `iblock` — они работают без коммерческого `catalog`.
  **Локалка на ноутбуке — точная копия прода:** движок `bitrix/` и база сняты с Reg.ru 2026-08-06,
  поэтому набор модулей ровно тот же, что в бою (прежняя локалка была триалом с полным набором,
  и расхождения всплывали только на проде).
- **Локальный сервер:** **Open Server Panel** (Apache + PHP 8.2 + MySQL-5.7). Путь зависит от машины:
  рабочий ноутбук — **v6.4 в `D:\OSPanel`**, прежний стационарный комп — v6.5.1 в `C:\OSPanel`.
  Скрипты определяют корень по расположению самого проекта, хардкода диска в них нет.
- **Папка сайта:** `<диск>:\OSPanel\home\latitudo-pro.local\` (`web_root` = эта папка).
- **Локальный домен:** `http://latitudo-pro.local/`, админка `…/bitrix/admin/`.
  Поддомены-филиалы локально: `msk.latitudo-pro.local`, `belgorod.…`, `vrn.…`, `krd.…`, `rnd.…`
  (алиасы прописаны в `.osp/project.ini` — имя секции обязано совпадать с именем папки; символ `_`
  недопустим, только буквы/цифры/дефис/точка, иначе OSPanel отбросит проект целиком).
- **База данных локально:** **MySQL-5.7** на `127.0.1.26`, база `latitudo_pro` (см. `bitrix/.settings.php`).
  Именно MySQL-5.7, не MariaDB — иначе Bitrix выдаст «Ошибка соединения с БД».
- **Запуск локалки:** `start-latitudo.cmd` в корне — **двойным кликом из проводника**. Сам он —
  ASCII-обёртка, вся логика в `tools/start-latitudo.ps1`. Стартует напрямую MySQL-5.7 (127.0.1.26),
  PHP-8.2 (127.0.1.35:9000) и Apache — **только то, что ещё не поднято**; ничего не гасит.
  Прямой запуск бинарников, а не CLI панели: у v6.4 CLI нет вовсе, у v6.5.1 `osp` не поднимает
  MySQL-5.7 и не работает из PowerShell.
  Два правила, на которых скрипт уже обжигался:
  **(1)** «поднято или нет» проверяем по занятому порту, а не по имени процесса — в системе
  крутится чужой `httpd.exe` (RAIDXpert2), и проверка по имени заставляла пропускать запуск Apache;
  **(2)** логика вынесена в `.ps1`, потому что cmd.exe разбирает батник в кодировке консоли и
  `chcp 65001` применяется не всегда — кириллица в комментариях ломала разбор целых блоков.
- **⚠️ Apache на ноутбуке запускается со СВОИМ конфигом** `.osp/apache/httpd-standalone.conf`
  (в `.gitignore`, лежит рядом с проектом). Причина: служба **RAIDXpert2** (веб-панель RAID от AMD,
  ставится с драйверами чипсета, работает под SYSTEM) держит `0.0.0.0:443`, и Apache OSPanel
  падает при старте — `AH00072: make_sock: could not bind to address 127.0.1.11:443`. Наш конфиг —
  копия конфига панели без всего, что слушает 443, плюс вхост проекта строкой `Use Host_PHP`
  (OSPanel 6 собирает вхосты через mod_macro). Пересобрать после обновления OSPanel:
  выбросить строки `Listen …:443` и `Use Host_Default_SSL`, дописать `Use Host_PHP` перед
  `UndefMacro`. Альтернатива — отключить службу RAIDXpert2 (нужны права администратора),
  тогда заработает штатный запуск через интерфейс панели.
- **Локалка работает по `http://`**, HTTPS локально не настроен — по `https://` будет
  «соединение не установлено». Это нормально; браузеры, пробующие HTTPS первым,
  откатываются на http. Закладки лучше держать с явным `http://`.
  **Историческая ловушка (закрыта 2026-08-07):** раньше `https://` на любом локальном
  домене отдавал страницу **XAMPP** — отвечал Apache службы RAIDXpert2
  (`C:\Program Files (x86)\RAIDXpert2\apache`, сборка на XAMPP), слушавший `0.0.0.0:443`,
  то есть все локальные адреса разом. Выглядело как «сайт сломался».
  Служба `Apache2.4` от RAIDXpert2 **остановлена и переведена в Disabled**, порт 443
  свободен. Сам RAID это не затрагивает — служба обслуживала только веб-панель.
  Вернуть: `Set-Service Apache2.4 -StartupType Automatic; Start-Service Apache2.4`
  (из PowerShell от администратора). Служба `rc_cgi` не тронута.
  Следствие: свой конфиг `httpd-standalone.conf` больше не обязателен — штатный запуск
  через интерфейс OSPanel теперь тоже не должен падать на 443. Скрипт запуска по-прежнему
  предпочитает свой конфиг, если файл на месте; переключаться не обязательно.
- **Домены локально прописаны в `hosts`** (`127.0.1.11` → `latitudo-pro.local` и 7 поддоменов):
  панель их не добавляет, потому что окружение поднимаем в обход неё.
  Соседний проект `latitudo-newdesign.loc` (копия latitudo.ru на Aspro Next) — на `127.0.1.12`,
  это ДРУГОЙ сайт в другой папке, не путать с нашим.

  Деплой: `git push` → `ssh regru-latitudo "cd www/latitudo.pro && git pull"`.
  ⚠️ **Beget-мост больше не нужен**: с ноутбука порт 22 `vip300.hosting.reg.ru` отвечает напрямую
  (проверено 2026-08-06), алиас `regru-latitudo` в `~/.ssh/config` настроен без `ProxyCommand`.
  ✅ Ключ на проде установлен (проверено 2026-08-17) — автономный деплой работает.
