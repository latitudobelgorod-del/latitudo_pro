# Как мы работаем над сайтом Latitudo

Короткая памятка для команды. Сайт состоит из **трёх частей** — важно не путать, где что меняется.

| Часть | Где живёт | Кто и как меняет |
|---|---|---|
| **Контент** (тексты, фото, телефоны городов, разделы каталога) | База данных на **проде Reg.ru** | Прямо в админке прода, вживую |
| **Включаемые области** (`/include/*.php` — «Как мы работаем», «О компании» и т.п.) | **Файлы, в Git** — но правятся в админке | В админке прода → потом забрать в репозиторий, см. регламент ниже |
| **Код** (шаблон, CSS, вёрстка) | Папка `/local`, в Git | Локально → `git push` → деплой на сервер |
| **Движок** `/bitrix/` | Только на серверах | Не трогаем, в Git его нет |

## Рабочий процесс

### Контент → меняем на проде
Тексты, картинки, телефоны и т.п. — правим **в админке прода Reg.ru**. База одна,
изменения сразу видны всем. В Git контент не попадает (это нормально).
⚠️ В админке старого стенда Beget контент больше не правим — эти изменения на прод не попадут.

### Включаемые области → правим в админке, но забираем в Git
Блоки «Как мы работаем», «О компании», «Преимущества» и прочие из папки `/include/` —
это **файлы под git**, хотя правятся визуальным редактором админки, как обычный контент.
Отредактировали такой блок на проде — он разошёлся с репозиторием и молча ждёт.

Чем это кончается: очередной `git pull` на проде падает с «Your local changes would be
overwritten by merge» и деплой встаёт. Так уже было 2026-07-24 — и с `urlrewrite.php`,
и с `include/how-we-work.php`, где правки копились месяцами.

**Правило: поправили включаемую область в админке — сразу заберите её в репозиторий.**
Не «когда-нибудь», а в тот же день: чем дольше расхождение живёт, тем страшнее его разбирать.

Проверить, есть ли расхождения (безопасно, ничего не меняет):
```
ssh regru-latitudo "cd www/latitudo.pro && git status --short"
```
В выводе допустим только `?? yandex_*.html` — файл подтверждения Яндекса, он вне git намеренно.
Всё, что помечено `M`, — это несохранённые правки, которые надо забрать.

Забрать файл с прода в репозиторий:
```
ssh regru-latitudo "cd www/latitudo.pro && base64 -w0 include/how-we-work.php" > tmp.b64
base64 -d < tmp.b64 > include/how-we-work.php     # берём байт-в-байт, иначе конфликт вернётся
git add include/how-we-work.php && git commit -m "content: блок «Как мы работаем» с прода"
git push
```
После этого на проде `git checkout -- include/how-we-work.php && git pull`.

⚠️ **Перед `git checkout --` на проде обязательно сверьте хэши** — эта команда стирает правки
без спроса, а в них живой контент, которого больше нигде нет:
```
git rev-parse HEAD:include/how-we-work.php                                  # локально
ssh regru-latitudo "cd www/latitudo.pro && git hash-object include/how-we-work.php"
```
Совпали — отбрасывать нечего, содержимое одинаковое, `checkout` безопасен.

### Особый случай: `urlrewrite.php` — правки идут в обратную сторону

Этот файл переписывает **сам Битрикс**, когда правила пересохраняются в админке. Он
пересобирает массив из своего представления и при этом **вырезает все комментарии**
(и добавляет хвостовые пробелы после `N =>`). Правила и их порядок при этом не меняются.

Поэтому здесь забирать с прода нечего — наоборот, **возвращаем версию из репозитория**:
комментарии в ней объясняют, почему правило-диспетчер лендингов обязано оставаться
последним в массиве. Сверьте, что расхождение действительно только в комментариях, и:
```
ssh regru-latitudo "cd www/latitudo.pro && git diff --stat urlrewrite.php"   # ожидаем ~2 вставки / 12 удалений
ssh regru-latitudo "cd www/latitudo.pro && git checkout -- urlrewrite.php"
```
Так было сделано 2026-08-06; предыдущая версия с прода сохранена на сервере
в `~/removed-from-site-2026-08-06/`.

Если же в diff видны изменения самих `CONDITION`/`PATH`/порядка — значит в админке
завели новое правило, и его надо забирать в репозиторий обычным порядком (выше).
**Не совпали — не отбрасывать:** на проде есть правки, которых нет в вашем коммите,
их сначала надо забрать (шаг выше) и только потом повторить сверку.

Города в таких блоках не зашиваем: пишем плейсхолдеры `#REGION_NAME_DECLINE_PP#`,
`#REGION_ADDRESS#` и т.п. — их подставит по поддомену обработчик из `region.php`
(полный список — в `local/php_interface/include/region.php`).

### Код → меняем через Git
1. Правим код **локально** (своя OSPanel).
2. Отправляем в GitHub:
   ```
   git add -A
   git commit -m "что сделал"
   git push
   ```
3. Выкладываем на прод — в терминале (ISPmanager → «Shell-клиент» или свой SSH):
   ```
   cd ~/www/latitudo.pro && git pull
   ```
4. Если правки шаблона не видны — сбросить кэш Битрикса
   (Админка → Настройки → Очистить кэш).

### Автономный деплой через Claude
Claude (Claude Code) выполняет весь цикл сам, **без ручного терминала**:
правит код локально → `git push` → сам заходит по SSH на прод → `git pull`.

- Доступ: SSH-алиас `regru-latitudo` (в `~/.ssh/config`), вход по ключу `~/.ssh/regru_latitudo`.
  **Beget-мост (ProxyCommand) больше не нужен** — с рабочего ноутбука (2026-08-06) порт 22
  `vip300.hosting.reg.ru` отвечает напрямую. Мост оставался в конфиге со времён стационарного
  компа, где Reg.ru молчал для зарубежных IP из-за постоянно включённого VPN.
  ⚠️ На ноутбуке ключ в `~/.ssh/authorized_keys` прода **ещё не установлен** — до этого
  автономный деплой не работает, см. «Что осталось сделать» в конце файла.
- Сервер тянет GitHub своим read-only deploy-ключом (`~/.ssh/github_deploy` на сервере).
- Команда выкладки:
  ```
  ssh regru-latitudo "cd www/latitudo.pro && git pull"
  ```
- На практике: достаточно сказать Claude, что поменять, — результат смотришь на сайте.
- Старый стенд Beget тоже доступен: `ssh beget-latitudo "cd ~/latituty.beget.tech/public_html && git pull"`.

## Работа с двух компьютеров

Репозиторий и прод общие, локалка на каждой машине своя. Это нормально и специально
так устроено — но надо помнить, **что git переносит, а что нет**.

| Переносится через git | Не переносится, живёт на каждой машине отдельно |
|---|---|
| Код: `/local`, включаемые области `/include`, корневые PHP, `/tools` | Движок `/bitrix/` (~1.4 ГБ) |
| Документация, скрипты запуска | Медиа `/upload/` |
| | База данных |
| | `.htaccess`, `figma.token`, `.osp/`, `bitrix/.settings.php`, `.claude/settings.local.json` |

Правая колонка — не недосмотр: движок и медиа слишком тяжёлые, база у каждого своя,
а конфиги зависят от машины. Всё это ставится один раз при развёртывании локалки.

### Ежедневный порядок

```
git pull                    # НАЧИНАЯ работу
...правки...
git add -A && git commit -m "что сделал" && git push    # ЗАКАНЧИВАЯ работу
```

**Главное правило: не оставляйте незакоммиченное на машине, от которой уходите.**
На второй его не будет, а когда вернётесь — придётся разбирать расхождение руками.
Если ушли и вспомнили — не страшно: доделайте на второй машине, а на первой потом
`git checkout -- <файл>` (правки там всё равно устарели).

### Что устаревает само: база

Контент правится в админке прода, а локальная база — **снимок на момент развёртывания**.
После `git pull` код будет свежий, а тексты, фото и телефоны — те, что были при переносе.
На вёрстку это не влияет, но при работе с контентом сбивает с толку.

Проверить, насколько отстали, и перелить дамп с прода — просите Claude, это минут пять:
он снимает `mysqldump` на сервере, скачивает и заливает в локальную базу.

### Что сказать Claude на второй машине

```
Работаем над latitudo.pro, локалка на этой машине уже развёрнута.
Сделай git pull, проверь что сайт поднимается, и скажи, насколько
локальная база отстала от прода.
```

Если локалки на машине ещё нет — процедура развёртывания с нуля описана в `CLAUDE.md`;
добавьте фразу «Разрешаю установить SSH-ключ на прод самостоятельно», иначе Claude
не станет прописывать себе доступ к серверу и работа встанет на этом шаге.

### Запуск локалки не зависит от машины

`start-latitudo.cmd` корень OSPanel вычисляет от папки проекта (`C:\OSPanel` и `D:\OSPanel`
одинаково подходят), а состояние определяет по ответу самого сайта, а не по адресам
модулей — они у каждой установки OSPanel свои. Ничего не гасит: поднимает только то,
что не поднято.

## Правила, чтобы ничего не сломать

- ⛔ **Код на сервере напрямую не редактируем** — только локально и через `git push`.
  Иначе правки затрутся при следующем `git pull`.
- ⛔ **`.htaccess` не коммитим** — он разный на локали и на серверах.
  Эталон лежит в `.htaccess.example`.
  ⚠️ Из этого следует: **правки корневого `.htaccess` на прод сами не уезжают.**
  `git pull` его не трогает. Порядок такой: поправил локальный `.htaccess` → ту же
  правку внёс в `.htaccess.example` (он версионируется) → после деплоя перенёс её
  в `.htaccess` на сервере руками (через ispmanager или `ssh`). Забыл второй шаг —
  на локалке работает, на проде нет. Так уже было с ЧПУ для `/policy` и `/terms`.
  Правило, которое обязано уехать вместе с кодом, лучше класть во **вложенный**
  `.htaccess` (например `include/.htaccess`) — вложенные версионируются.
- ⛔ **Секреты (`figma.token`, пароли) в Git не кладём** — они в `.gitignore`.
- ✅ Контент — только в админке прода. Код — только через Git.
